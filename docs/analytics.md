# 방문자 확인하는 법

> 2026-08-25 신설. "실제 외부 방문자가 있는가"에 답하기 위한 설정과 확인 절차.

## 왜 만들었나

기존 집계(`bump_view` → `page_views` 테이블)는 **경로·조회수·시각만** 저장했다.
방문자를 구분하는 값이 하나도 없어서, 조회 128회가 찍혀 있어도
**소유주 본인의 접속인지 외부 방문자인지 알 수 없었다.** 그 구멍을 메운다.

---

## 확인처 세 곳 (목적이 다르다)

| 곳 | 무엇을 보나 | 켜는 데 필요한 일 |
|---|---|---|
| **Vercel Web Analytics** | 순 방문자·유입 경로·국가·기기 | **대시보드에서 켜기 (1회)** |
| **Google Search Console** | 검색 노출·클릭 — 100% 외부 | 이미 등록됨, 보기만 |
| **우리 Supabase** | 우리가 소유하는 원자료 | **SQL 1회 실행** |

## 1. Vercel Web Analytics — 가장 빨리 답을 준다

코드는 이미 들어가 있다(`Base.astro`, 정본 빌드에만 주입). **대시보드에서 켜기만 하면 된다.**

1. https://vercel.com → 프로젝트 선택
2. 상단 **Analytics** 탭 → **Enable** (Hobby 플랜 무료)
3. 켠 다음부터 수집 시작. 이전 방문은 소급되지 않는다.

보이는 것: **Visitors(순 방문자)** · Page Views · **Referrers(어디서 왔나)** · Top Pages · 국가 · 기기.

- **Visitors 가 진짜 답이다.** 조회수가 아니라 사람 수를 센다.
- **Referrers 에 `google.com`·`naver.com` 이 뜨면 검색으로 들어온 외부 방문자다.**
- 쿠키를 쓰지 않아 동의 배너가 필요 없다.

> 사장님 본인 접속도 함께 잡힌다. 본인 것을 빼고 보려면 Referrers 에서
> 검색엔진 유입만 보거나, 아래 2번(서치콘솔)을 본다.

## 2. Google Search Console — 외부 방문자만 순수하게

검색 노출·클릭은 **본인 접속과 절대 섞이지 않는다.** 가장 확실한 외부 신호다.

1. https://search.google.com/search-console → 속성 **`dotoriecon.com`**
2. 왼쪽 **실적(Performance)**
3. **총 클릭수**가 0이 아니면 → 검색으로 들어온 실제 방문자가 있다는 뜻
4. **총 노출수**만 있고 클릭이 0이면 → 검색 결과에 뜨긴 하는데 안 눌린다 (제목·설명 개선 신호)

네이버는 https://searchadvisor.naver.com → 사이트 → **검색 유입** 에서 같은 것을 본다.

> **지금은 0으로 나오는 게 정상이다.** 도메인을 2026-08-24에 취득했고,
> `site:dotoriecon.com` 검색에 아직 색인이 안 잡힌다. 새 도메인은 보통 며칠~몇 주 걸린다.
> 색인이 되기 전에는 검색으로 들어올 경로 자체가 없다.

## 3. 우리 Supabase — 데이터를 우리가 갖는다

Vercel·구글은 남의 대시보드다. 우리 원자료로도 갖고 있어야 매일 아침 Routine이
일지에 방문자 수를 기록할 수 있다.

### 최초 1회 적용

**딱 두 번 누르면 된다.**

1. SQL 원문 열기 → https://raw.githubusercontent.com/aijhmin1031-eng/blog.tradinfo-tory/main/scripts/sql/visit_log.sql
   (전체 선택·복사)
2. SQL 편집기 바로 열기 → https://supabase.com/dashboard/project/tfksqpxfpniavvnwfjiu/sql/new
   (붙여넣고 **Run**)

이걸로 `visit_log` 테이블과 함수 3개(`log_visit`·`visit_summary`·`visit_referrers`)가 생긴다.
클라이언트 코드는 이미 나가 있어서, **SQL만 돌리면 그 시점부터 자동으로 쌓인다.**
(적용 전까지는 호출이 조용히 실패할 뿐 사이트에 아무 영향이 없다.)

### 남기는 것 / 안 남기는 것

- **남긴다**: 그날치 난수 방문자값 · 경로 · 유입 도메인(`google.com`)
- **안 남긴다**: IP · 쿠키 · 기기 정보 · 전체 URL · 검색어
- 방문자 난수는 **자정이 지나면 새로 만들어진다.** 같은 사람을 이틀 이상 추적할 수 없다.
- 우리 도메인 내부 이동은 `internal`, 주소 직접 입력은 `direct` 로 접힌다.
  → **`direct`·`internal` 을 뺀 나머지가 외부 유입이다.**

### 확인 (SQL Editor에서)

```sql
-- 최근 14일: 날짜별 순 방문자 / 조회 / 외부 유입 방문자
select * from visit_summary(14);

-- 최근 14일: 어디서 들어왔나
select * from visit_referrers(14);

-- 최근 7일: 어느 글을 보았나 (2026-08-26 신설)
select * from visit_pages(7);

-- 최근 7일: 봇으로 걸러낸 것이 무엇이었나 (2026-08-26 신설, 오판 확인용)
select * from visit_bots(7);
```

**`visit_pages` 를 먼저 볼 것.** 방문자 수만 보면 사람인지 크롤러인지 알 수 없다.
**서로 다른 글을 하나씩만 훑은 방문자가 여럿**이면 사람이 아니라 크롤러 렌더링 패턴이다
(2026-08-26 에 실제로 이 모양이 나왔다 — 아래 「지금 상태」 참조).

---

### 적용 이력 (2026-08-25, 전부 완료)

1. `visit_log.sql` — 테이블·함수 3개 생성 ✅
2. `visit_log_fix_20260825.sql` — 홈 `/` 가 거부되던 경로 검증식 수리 ✅
   (첫 판이 슬래시를 두 개 요구해서, 가장 많이 보는 홈만 안 잡히고 있었다)
3. `visit_log_cleanup.sql` — 검증용 가짜 행 삭제 **+ 재발 방지**
   (방문자값 검증을 실제 형식인 16진수 16자로 좁혀, 손으로 넣은 값은 아예 기록되지 않게 했다.
   검증하다 통계를 더럽히는 일이 구조적으로 불가능해진다.)

**이후 새로 만들 SQL은 `visit_log.sql` 원본이 정본이다** — 위 수정이 반영돼 있다.

### 적용 이력 (2026-08-26 — **소유주가 한 번 더 돌려야 한다**)

`visit_log.sql` 에 **봇 판정과 경로별 조회**를 더했다. 적용 방법은 처음과 같다 —
[SQL 원문](https://raw.githubusercontent.com/aijhmin1031-eng/blog.tradinfo-tory/main/scripts/sql/visit_log.sql)
전체를 복사해 [SQL 편집기](https://supabase.com/dashboard/project/tfksqpxfpniavvnwfjiu/sql/new)에 붙여넣고 Run.
**전부 멱등이라 몇 번을 다시 돌려도 안전하다**(기존 기록은 지워지지 않는다).

무엇이 달라지나.

1. **봇을 버리지 않고 표시해서 남긴다.** `visit_log` 에 `bot`·`bot_hint` 두 칸이 붙는다.
   조회 함수 셋은 전부 `bot = false` 만 센다. **걸러낸 것은 `visit_bots()` 로 눈으로 볼 수 있다.**
   조용히 버리면 필터가 사람을 지워도 영원히 모른다 — 그래서 남긴다.
2. **판정은 서버가 한다.** PostgREST 가 넘겨주는 `request.headers` 의 User-Agent 를 본다.
   크롤러는 우리 JS 를 실제로 실행하므로 클라이언트 판정만으로는 못 막는다.
   **헤더를 못 읽는 환경이면 판정을 아예 하지 않는다**(fail-open) — 막는 쪽으로 잘못 넘어가면
   방문 기록이 통째로 0이 되고 그것이 조용히 일어난다. 이 저장소는 그 사고를 이미 겪었다.
3. **`visit_pages(n)`·`visit_bots(n)` 함수가 생긴다.**

적용 전까지는 새 함수 호출이 `PGRST202`(함수 없음)로 떨어질 뿐, 사이트에는 아무 영향이 없다.

## 보고는 어디로 오나

매일 아침 Routine이 방문자 수를 읽어 **세 곳**에 남긴다(worklog 「상시 운영」 ⑦-2).
대시보드를 직접 열 필요가 없다.

| 경로 | 언제 | 무엇이 |
|---|---|---|
| **폰 푸시 알림** | 실행 끝나면 바로 | 보고 **첫 줄**의 «어제 방문자 N명(외부 M명)» |
| **세션 기록** (claude.ai/code) | 푸시를 누르면 | 그날 점검 전문 |
| **`docs/worklog.md`** | 커밋과 함께 | 영구 기록 — 나중에 되짚을 원본 |

Routine 알림 설정은 `push: true · email: false`.
**이메일로도 받고 싶으면 트리거를 다시 만들어야 한다**(현재 도구로는 알림 채널만 따로 못 바꾼다).
그때 트리거 ID가 바뀌므로 이 문서와 worklog의 ID 표기도 함께 고칠 것.

## 숫자를 볼 때 주의할 것

기사에 적용한 기준과 같다 — **그럴듯한 해석을 검증 없이 쓰지 않는다.**

- 방문자 한두 명의 변화로 추세를 말하지 않는다. 표본이 너무 작다.
- 조회수(pageviews)와 방문자(visitors)를 섞어 쓰지 않는다. 늘 어느 쪽인지 밝힌다.
- 봇·크롤러가 섞일 수 있다. `direct` 가 갑자기 튀면 유입이 아니라 크롤러를 의심한다.
  2026-08-26 부터 서버가 User-Agent 로 걸러내지만 **완벽하지 않다** — UA 를 브라우저로 위장하는
  크롤러는 지금도 사람으로 잡힌다. `visit_pages()` 의 모양(서로 다른 글을 하나씩)으로 한 번 더 의심할 것.
- **필터를 의심하는 것도 일과다.** `visit_bots()` 에 이상한 낱말이 올라오면 사람을 지우고 있는 것이다.
  낱말은 `scripts/sql/visit_log.sql` 의 `v_bot` 정규식에서 빼면 된다.
