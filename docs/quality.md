# 품질 관리 체계

> 2026-08-25 신설 (소유주 지시: "블로그 글의 품질 관리 체계를 제대로 갖추라").
> 규칙이 여러 문서에 흩어져 있고 **전체를 시간에 따라 재는 장치가 없던 것**을 정리한다.

## 왜 체계가 필요했나

8/25 전수 진단에서 나온 것들은 개별 실수가 아니라 **장치가 없어서 생긴 일**이었다.

- 기사가 원인을 틀리게 지목한 채 발행됐다 → **검정 단계가 없어서**
- 104편 전부에 같은 출처 문자열이 박혀 있었다 → **기사별 출처 칸이 없어서**
- 읽기 시간이 4배 부풀려져 있었다 → **손으로 적고 있어서**
- 홈 화면에서 같은 숫자를 세 번 읽게 했다 → **부품별 역할이 안 갈려 있어서**

사람(혹은 AI)이 매번 잘하기를 기대하는 대신, **틀리면 걸리는 자리**를 만든다.

## 4층 구조 (2026-08-26 개편 — 3층에서 한 층 늘었다)

| 층 | 무엇을 | 언제 | 어디에 |
|---|---|---|---|
| **① 기준** | 어떻게 쓸 것인가 | 쓰기 전 | `operations.md` 「기사 집필 기준」 |
| **② 게이트** | 이 한 편이 **형식**을 지켰나 | 커밋 전 | `scripts/check-quality.mjs` |
| **③ 감사** | 전체 중 **내용**이 무른 기사는 어느 것인가 | 커밋마다 · 아침 | `scripts/audit.mjs` |
| **④ 지표** | 블로그 전체가 나아지고 있나 | 매일 | `scripts/quality-metrics.mjs` |

네 층은 서로를 대신하지 못한다. 기준만 있으면 안 지켜지고, 게이트만 있으면
"오늘 쓴 글이 형식을 지켰나"까지만 알며, 지표만 있으면 개별 기사를 막지 못한다.
**③이 8/26에 새로 생긴 층이다.** 왜 필요했는지는 바로 아래.

### ③ 감사가 왜 필요했나 (2026-08-26)

두 사고가 같은 뿌리에서 나왔다.

1. **목록이 낡았다.** 품질 관리가 `docs/backfill-queue.md` 라는 **손으로 뽑은 목록** 위에
   서 있었다. 목록은 8/25 에 만들어졌고 기사는 매일 2편씩 는다. 그래서 큐 밖의 데이터 기사
   14편이 링크 0개로 남아 있었다(Tier C 를 급히 신설해 메웠다).
2. **게이트가 형식만 봤다.** 게이트는 "`sources` 배열이 있는가"를 묻지 "이 수치로 한 주장에
   근거가 붙어 있는가"는 묻지 못한다. 그래서 `semi-import-paradox` 는 수출입이 동행한다고
   **주장만 한 채** 게이트를 통과해 서 있었다. 상관계수를 실제로 재 보니 수준 기준 R² 94.7%가
   증감률 기준으로는 38.9%였고, 대만은 3.6%로 설명을 배신했다.

그래서 **목록을 버리고 매번 전수로 계산한다.** 목록은 낡지만 기준은 안 낡는다.

```bash
npm run audit                      # 전수 감사, 손볼 순서대로
npm run audit -- --fail-on=90      # 검정 없음·출처 없음이 있으면 종료코드 1 (CI가 쓰는 것)
npm run audit -- --strict          # 하나라도 걸리면 종료코드 1 (커밋 훅이 쓰는 것)
npm run audit <슬러그>              # 지정한 기사만
```

**무엇을 보나** (괄호는 가중치, 높을수록 먼저 손본다)

| 가중치 | 항목 | 뜻 |
|---:|---|---|
| 100 | 검정 없음 | 우리 수치로 인과·동행을 주장하는데 반증 시도가 없다 |
| 90 | 출처 없음 | `sources` 가 비었다 |
| 80 | 끝맺음 없음 · 긴 대시 | 절대 규칙 위반 |
| 60 | 링크 0개 | 독자가 다음에 읽을 곳이 없다 |
| 55 | 리드 비두괄식 | 첫 문단에 결론 수치가 없다 (2026-08-26 신설) |
| 50 | 소제목 무수치 | 발견을 수치로 말하는 소제목이 없다 (2026-08-26 신설) |
| 45 | 표 없음 | 나열·대조가 줄글에 묻혀 있다 (2026-08-26 신설) |
| 40 | 얇음 | 검정도 없이 900자 미만 |
| 30 | 도입부 재탕 · PointCards 겹침 | 같은 말을 두 번 읽힌다 |

신설 3종은 **90 미만이라 CI 빨간불을 켜지 않는다.** 기준을 새로 올린 것이지 기사가
나빠진 것이 아니므로, 감사 일과가 순서대로 처리한다(착수 시점 실측: 소제목 무수치 94편 ·
리드 비두괄식 91편 · 표 없음 33편). 규칙 원문은 `operations.md` 「4. 인용 가능성 3종」.

**어휘로 판정한다는 한계를 알고 쓸 것.** 「주장」은 인과 어휘와 **숫자가 같은 문장**에 있을 때만
센다(그냥 어휘만 보면 평범한 설명문까지 걸린다. 실측에서 14편 중 절반이 위양성이었다).
그래서 감사는 **걸린 문장을 그대로 인쇄한다.** 위양성이면 사람이 3초 만에 기각하면 된다.
기각한 판정을 스크립트에 예외로 박아 넣지 말 것. 예외 목록은 곧 낡고, 낡은 예외는 구멍이 된다.

## ① 기준 — 쓰기 전

원문은 `operations.md`. 핵심만 옮기면:

- **검정 문단**: 숫자로 인과를 주장하면 반증을 시도한 문단을 함께 싣는다. 대조군 필수.
- **출처**: 프런트매터 `sources`에 **확인한 것만**. 지어낸 주소는 무출처보다 나쁘다.
- **끝맺음**: 데이터 기사는 「다음에 확인할 것」(지표+기준선), 설명 기사는 「실무에서 틀리기 쉬운 지점」.
- **두괄식**: 본문 첫 문단에 결론 수치를 적는다. 소제목 하나는 수치형으로. 표는 최소 1개.
  (2026-08-26 신설 — `operations.md` 「4. 인용 가능성 3종」)
- **반복 금지**: 요점3줄·KeyStat 을 첫 문단이 **표현까지 그대로** 옮기지 않는다.
  두괄식 리드가 그 수치를 다시 말하는 것은 규칙이 시키는 일이니 재탕이 아니다.
  PointCards는 본문 요약이 아니라 **새 각도**를 준다.
- **긴 대시(—) 금지**, 문단 350자 이하, 내부 링크는 **발행된 기사만**.

**쓰기 전에 반드시:**

```bash
npm run linkable      # 지금 링크 걸어도 되는 기사 목록 (죽은 링크 예방)
```

## ② 게이트 — 커밋 전 (형식)

```bash
npm run check-quality <슬러그>     # 한 편
npm run check-quality -- --all     # 큐 전체
```

**실패(커밋 금지)**: 출처 없음 · 「오늘의 결론」 잔존 · 새 끝맺음 없음 · 긴 대시 ·
물타기(150자 넘게 늘었는데 출처 그대로) · 죽은 내부 링크
**경고**: 확인 URL 없음 · 1,300자 미만 · 내부 링크 0개 · 문단 350자 초과 ·
장식용 표(2행 미만·2열 미만) · 숫자 표에 단위 없음 · 리드에 기준시점 없음

**인용 가능성 3종 — 신규는 실패, 기존은 경고** (2026-08-26 소유주 지시, 규칙 원문은
`operations.md` 「4. 인용 가능성 3종」):

| 검사 | 뜻 | 신규 | 기존 |
|---|---|---|---|
| 두괄식 리드 | 본문 첫 문단에 결론 수치 | 실패 | 경고 |
| 핵심 발견 소제목 | 소제목 하나에 숫자 | 실패 | 경고 |
| 표 최소 1개 | 비교 축 둘 이상 | 실패 | 경고 |

신규·기존을 가르는 것은 `origin/main` 에 그 파일이 있는가다(물타기 검사와 같은 기준).
**기존 107편을 한꺼번에 빨갛게 켜면 빨간불이 상시가 되고, 상시가 된 경고는 안 보게 된다.**
기존분의 처리 **순서**는 ③ 감사가 정한다.

> 게이트는 **사후 검사**다. 걸린 뒤 고치면 두 번 일한 것이다.
> `operations.md` 「쓰기 전 체크리스트」를 먼저 볼 것.

## 규칙이 실행되는 자리 (2026-08-26)

문서에 적어 둔 규칙은 **안 읽히면 그만**이다. 8/25~26 사고 두 건 모두
"문서에는 적혀 있었다". 그래서 규칙을 **실행되는 자리**로 옮겼다.

| 자리 | 무엇이 도나 | 성격 |
|---|---|---|
| **커밋 훅** `.githooks/pre-commit` | staged 된 기사에 대해 게이트 + 감사(`--strict`) | 옵트인, 로컬 |
| **CI** `deploy.yml` 의 `품질 점검` job | 게이트 전수 + `precheck` + 감사(`--fail-on=90`) | 항상, 푸시마다 |

**커밋 훅 켜기**(저장소마다 한 번):

```bash
git config core.hooksPath .githooks     # 켜기
git commit --no-verify                  # 이번 한 번만 건너뛰기
git config --unset core.hooksPath       # 끄기
```

**CI 는 배포를 막지 않는다.** `품질 점검`은 `build`·`deploy` 와 **의존 관계가 없는 별도 job**이다.
살아 있는 사이트에서 게이트가 배포를 막으면 기사 한 편의 흠 때문에 사이트 전체가 멎는다.
대신 커밋마다 빨갛게 남겨서 **발행일 아침이 아니라 쓴 날** 결함이 보이게 한다.

**빨간불은 아껴서 켠다.** CI 감사는 `--fail-on=90`, 즉 「검정 없음·출처 없음」에만 켠다.
얇음·재탕까지 빨갛게 켜면 빨간불이 상시가 되고, **상시가 된 경고는 아무도 안 본다.**

## ④ 지표 — 매일

```bash
npm run quality          # 현재 지표 + 지난 스냅샷 대비 증감
npm run quality:save     # 위 + data/quality-history.json 에 기록
```

`data/quality-history.json` 이 시계열이다. 이걸로 "지난달보다 나아졌나"에 답한다.

### 지표 정의와 방향

| 묶음 | 지표 | 좋은 방향 | 뜻 |
|---|---|---|---|
| **깊이** | 평균·중앙 분량 | ↑ | 얕은 해설을 벗어나는 정도 |
| | 1,500자 이상 비율 | ↑ | 애드센스 심사 통념선을 넘는 비율 |
| **근거** | 출처 보유율 | ↑ | 독자가 원자료로 되짚어 갈 수 있는 비율 |
| | 확인 URL 보유율 | ↑ | 출처가 이름뿐이 아닌 비율 |
| | 검정 흔적 보유율 | ↑ | 반증을 시도한 흔적이 있는 기사의 비율(전체 분모) |
| | **★ 주장 기사 중 검정 보유율** | ↑ **100%가 목표** | **분모가 「검정이 필요한 기사」다.** 해설 기사에까지 상관계수를 요구하면 지표가 물타기를 부추긴다. 이 칸만은 목표로 삼아도 되는 유일한 칸이다 |
| **반복** | 도입부 재탕 기사 수 | ↓ | 같은 숫자를 세 번 읽게 하는 기사 |
| | PointCards 재탕 기사 수 | ↓ | 요약 카드가 본문을 되풀이하는 기사 |
| **연결** | 평균 내부 링크 | ↑ | 체류 시간 |
| | 내부 링크 없음 비율 | ↓ | 막다른 기사 |
| | 실데이터 사용 비율 | ↑ | 매일 갱신되는 기사의 비율 |
| | 쓰이는 데이터 계열 | ↑ | 수집만 하고 노는 데이터가 없는가 |
| **형식** | 「오늘의 결론」 잔존 | ↓ | 템플릿 해체 진행도 |
| | 긴 대시·긴 문단 위반 | ↓ | 절대 규칙 준수 |

### 지표를 다룰 때의 원칙

- **지표를 목표로 삼지 않는다.** 숫자를 올리려고 글을 쓰면 물타기가 된다.
  지표는 결과를 확인하는 자이지 글쓰기의 목적이 아니다.
- **하나의 종합 점수를 만들지 않는다.** 합치면 어디가 나빠졌는지 안 보인다.
- **표본이 작을 때 추세를 말하지 않는다.** 한두 편 변화로 방향을 논하지 않는다.

## 기준선 (2026-08-25, 107편)

체계를 세운 날의 값. 앞으로 이 줄과 비교한다.

| 지표 | 기준선 8/25 | 8/26 (보강 큐 100편 완주 후) |
|---|---:|---:|
| 평균 분량 | 998자 | **1,425자** |
| 1,500자 이상 | 7.5% | **32.7%** |
| 출처 보유 | 22.4% | **100%** |
| 확인 URL 보유 | 22.4% | **100%** |
| 검정 흔적 보유(전체) | 2.8% | 14.0% |
| ★ 주장 기사 중 검정 | (측정 안 됨) | **37.5% (8편 중 3편)** |
| 도입부 재탕 | 8편 | 5편 |
| PointCards 재탕 | 3편 | **0편** |
| 평균 내부 링크 | 0.2개 | **1.5개** |
| 내부 링크 없음 | 88.8% | **0%** |
| 실데이터 사용 | 16.8% | 24.3% |
| 쓰이는 데이터 계열 | 13/25 | 13/25 |
| 「오늘의 결론」 잔존 | 80편 | **0편** |
| 끝맺음 없음 | 83편 | **0편** |

**8/25에 가장 나빴던 두 칸(내부 링크 없음 88.8%·출처 보유 22.4%)은 메웠다.**
**남은 최악의 칸은 「주장 기사 중 검정 37.5%」다.** 우리 수치로 인과를 주장하는 기사 8편 중
5편이 반증을 시도하지 않았다. 이것이 다음 보강 대상이고, CI 가 이 칸을 이유로 빨간불이다.

> **「검정」 지표의 정의가 8/26에 바뀌었다.** 이전에는 `## 검정` 이라는 **제목 글자**만 셌다.
> 그래서 제목을 「정말 동행하는가, 재 보았다」로 단 기사는 상관계수·대조군을 다 싣고도 0으로
> 잡혔다. 지금은 제목이 아니라 반증을 시도한 **흔적**(상관계수·결정계수·대조군·표본 등)을 센다.
> 8/26 이전 스냅샷의 「검정」 값과 직접 비교하지 말 것.
